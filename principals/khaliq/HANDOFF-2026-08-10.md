```

  → validate → deploy via SST → verify the live engine

```

**The migration** (`0034_node_load_reporting.sql`, already on main and published)
adds `load_reported INTEGER NOT NULL DEFAULT 0` to `nodes` and `node_providers`
and corrects broker aggregates to `max_agents=0` when any provider is unbounded.
**Forward-safe yes; reversible NO** — no down migration, and dropping columns on
SQLite/D1 needs a table rebuild. Know that before the cloud upgrade, not during.

**One precision worth carrying:** the raw `load` cell is still `NOT NULL` and *is*
`0` when `load_reported=false`. The authoritative value is the **pair
`(0, false)`** — zero alone never means unknown, public reads return `null`, and
placement treats it as unknown. "Never coerced to `0`" holds by **provenance, not
nullable storage**.

## 3. How to work here — earned the hard way tonight

Full detail in `memory/learnings.md`. The ones that cost the most:

- **An unread inbox is a Chief defect.** "No commits" and "no answer" are
  different claims. A lane blocked on a decision correctly produces no commits.
- **A change-detector cannot see termination.** I swept `cloud#2917` for twelve
  hours reporting "no new checkpoints." It had been **closed** the whole time.
  Re-read the object's own `state`, not just its activity.
- **Never hand a lane your hypothesis as its brief.** I did it twice; both were
  wrong and both anchored the lane. Brief the symptom, ask for the diagnosis.
- **"Disabled" and "unreachable" are different claims.** Only the second licenses
  closing a review thread.
- **A code-search miss is not absence.** `gh api search/code` returned 0 for a
  dependency that a local `grep` found immediately.
- **Verify from the registry, not the workflow.** A green publish job is not a
  published package.
- **Do not declare a lane dead on a 25-minute window.** I called four dead; at
  least two were simply working, and I spawned duplicate twins that then had to
  be stood down.
- **Chief does not implement.** I dispatched a publish myself; Khaliq corrected
  me. The lead owns the release, Chief gates it.

## 5. The handoff itself — and why it is not complete

`CLAUDE.md` §7: *a handoff replaces a session, never the Chief's address.* The
canonical name in `teams.json` is **`chief-khaliq`**, and the handoff is complete
only when a process runs under that exact name and answers a liveness probe
through it.

**That cannot be done by spawning while the incumbent is alive.** On this broker
(11.4.2, pre-`#1464`) a duplicate-name spawn returns `{spawned:true}` and starts
nothing — verified by experiment tonight, both arms. So a successor necessarily
starts under a temporary name and **shadows**.

Per §7 the shadow **must not become the durable Chief**, and the rostered resident
**must not stand down merely because the shadow is alive**. If the canonical name
cannot be reacquired, **keep the incumbent online and page Khaliq** — do not
declare a renamed successor to be continuity.

**So the honest state to report: the shadow holds the context, the address is
still held by the incumbent, and closing that gap is Khaliq's call.**
