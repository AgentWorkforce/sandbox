## Learned

- **The fleet restart killed every `-0810` lead.** 11 of 14 active workstreams
  had an owner that no longer existed. The tell was mass-identical `lastSeen`
  values — `22:37:57Z` for one cohort, `22:34:13Z` for another — which by the
  brain's own rule is a stamp event, not a death time. Only the three residents
  in `teams.json` came back, because only they are rostered.

- **A node's capability list does not gate spawns, and I was wrong to infer that
  it did.** `barry` advertised `spawn:persona` as an *action*; `chief-broker`,
  `finn-mini` and `sf-mini` advertised only `spawn:*` *capacity*. I concluded the
  other three could not receive a fleet spawn. **Khaliq said to double-check, and
  a direct spawn on `finn-mini` succeeded immediately** — as did `sf-mini` on a
  retry. The capability list is a registration record; the discriminating test is
  an actual spawn. I had the instrument and reasoned from the registry instead.

- **`chief-broker` is absent from the fleet node registry.** `query_nodes` with
  `name: "chief-broker"` returns `[]`, and a fleet spawn targeting it fails
  `Node "chief-broker" not found` — even though the same name appeared as
  `online` in a full listing minutes earlier, its agents run, and its broker is
  healthy. **The local path is unaffected:** `agent-relay node agent spawn
  <provider> --cwd <path>` works and is how four of tonight's leads were placed.
  So this is a fleet-registration gap, not an outage — remote fleet spawns cannot
  target this machine.

- **`--cwd` on the local spawn is the fix for the placement hazard.** "A node is
  available" is not "a node can do this work", and repo access never comes from
  the node being up. Setting `--cwd` explicitly makes repo access deterministic
  instead of hoping the agent lands somewhere useful.

- **Dispatched is not running.** `sf-mini` returned `status: "dispatched"` with a
  real `dispatchedNodeId`, and `cloud-identity-lead-0811` never appeared in the
  control plane at all. The first attempt returned `status: "pending"` with a
  null dispatch target and also produced nothing. An invocation record is a
  record write.

- **`pr-shepherd` and `intent-trajectory-lineage` are one spine, not two
  workstreams.** pr-shepherd V1 item 4 ("carry the spec — hold the originating
  intent … answer *what was this for and is it still true?*") and item 5 ("trace
  to production: intent → issue → PR → merge → deploy") are Khaliq's trajectory
  doctrine already written as agent requirements, months before he restated the
  doctrine tonight. Their leads were told to agree a boundary in writing.

- **The doctrine about making intent durable was itself lost by being only
  spoken.** Khaliq described the intent→trajectory chain to a previous Chief. A
  search of relay history and the entire brain finds no record of that
  conversation.

- **292 open PRs org-wide in AgentWorkforce, 239 non-draft** (measured 22:47Z).
