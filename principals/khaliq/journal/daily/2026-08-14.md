# 2026-08-14

Two independent incidents ran concurrently in the afternoon: an agent-relay
release regression that broke agent-to-agent DMs fleet-wide, and a Factory
durable-object overload. Separately, Chief's own relay identity went dead and
is still unrecovered at end of day.

## Shipped

- **`relay#1518` — dm send unblocked.** `agent-relay` 11.6.2 (published
  10:23:04Z) broke `message dm send` fleet-wide with `Workspace key required
  (rk_live_...)`, even with the key present in env and passed explicitly.
  `message post`, `agent list`, `fleet nodes`, and `status` were unaffected —
  the break was `dm send` alone, failing at a workspace-only roster read
  *before* authenticating. `relay-lead-0814` isolated it with a control arm on
  `finn-mini` (still on 11.5.4: same credentials, same command, returned a
  `conversationId`), spawned the `relay-dmfix` lane there at 14:23 —
  deliberately off `chief-broker`, which had the broken CLI — and the fix
  merged and released as 11.6.3 at 13:21:42Z, inside an hour.
  Commit `75e969a96 fix(cli): stop dm send from blocking on a workspace-only
  roster read (#1518)`.

- **Factory production upgraded 0.1.20 → 0.1.58** and 8 issues filed during the
  incident (per `factory-lead`; not independently verified by Chief).

## Learned

- **The updater trusted a stale cache and silently reinstalled the same
  version.** `update-cache.json` recorded `latestVersion: 11.6.2` at ~13:45,
  before 11.6.3 existed. A subsequent upgrade rewrote both binaries at 15:22
  with **byte-identical sizes** and `--version` still reporting 11.6.2 — a
  no-op that looked exactly like a successful upgrade. Deleting the cache and
  re-running `update --check` immediately surfaced 11.6.3. Verify an upgrade by
  reading the version back, never by the absence of an error.

- **`agent-relay update` installs to a different path than the one agents
  run.** It put 11.6.3 in npm-global/mise, which shadowed the old binary for an
  interactive shell while `~/.agentworkforce/relay/bin/agent-relay` — the copy
  the broker and node actually execute — stayed on 11.6.2. For a period the
  CLI on PATH was fixed and the fleet's CLI was not. All paths converged to
  11.6.3 at 15:34.

- **The install is rename-based, so running processes are safe.** The running
  broker (pid 1316) and node (pid 1311) still hold the *old* inodes while disk
  carries new ones. No code-signing SIGKILL, no crash reports. But they
  continue executing the old image until restarted — and restarting the node
  kills every agent on it, so version drift between disk and memory is the
  normal state, not an anomaly.

- **Skip.app's crash takes the resident Chief down with it.** Skip 0.1.0
  crashed at 13:35:52 +0200, `SIGTRAP` / `EXC_BREAKPOINT`, faulting thread
  `com.apple.root.user-initiated-qos.cooperative`:
  `AgentClient.stopAutoHeartbeat()` ← `AgentClient.startAutoHeartbeat()` ←
  `closure #1 in AgentClient.connect()`, crashing inside
  `swift::AsyncTask::~AsyncTask` / `destroyTask`. A Swift-concurrency fault
  destroying the previous heartbeat task on the **reconnect** path — so relay
  churn is a trigger. Its 14:21:34 relaunch respawned `chief` at 14:22:38
  (broker record: `parent: "Dashboard"`). Chief cycled at least three times
  between 14:03 and 14:22. Crash report:
  `~/Library/Logs/DiagnosticReports/Skip-2026-08-14-133552.ips`.

- **A released seat produces an invalid token that no documented path
  re-mints.** See In flight.

- **Factory was re-enumerating the whole issue tree every cycle** — 6,674
  `listTree` calls with one subtree listed 67 times — overloading the relayfile
  workspace durable object into `429 durable_object_overloaded`. Filed as
  `factory#259` (per `factory-lead`).

## Decided

- **Chief's canonical name was not reacquired, and no renamed successor was
  declared.** Per the operating manual, the resident stayed online and the
  principal was paged instead. Chief communicated through a temporary
  identity with an explicit first line stating it is Chief and that the sender
  name is a workaround — labelled, not impersonated.

- **`agent remove` + re-register was rejected as a recovery route** for the
  `chief` seat, before it was attempted on the canonical record. Confirmed
  correct afterwards: the command is broken (see In flight).

## In flight

- **Chief's relay seat is dead and unrecovered.** The Relaycast record for
  `chief` (`id 208672157419945984`) carries
  `release: { reason: null, released_at: "2026-08-14T12:06:00.842Z" }`. That
  invalidated the agent token; the fleet-watchdog tripped
  `MISSING_RESIDENT: chief` at 12:08:40Z, ~2.5 minutes later. Every respawn
  since has been handed the same pre-release token from local config and fails
  `Invalid agent token` on post, dm, and inbox alike, through both CLI and MCP.
  **What released it, and why, is unknown.** Chief is still mute.

- **Three relay defects surfaced by the recovery attempt**, briefed to
  `relay-lead-0814` for lane assignment and filing:
  1. The null-reason seat release above.
  2. **`agent remove` fails and leaks raw SQL** — returns
     `Failed query: delete from "agents" where "agents"."id" = ?` with the
     parameter, straight to the caller. Two defects in one, and it closes off
     remove-and-re-register as a recovery route.
  3. **`register_agent` hangs on the broken name** — on 11.6.2 it returned the
     *same dead token* instantly; on 11.6.3 it hangs past 120s with no
     response. Fresh names register in under a second.

- **The remediation loop.** The server's own error text instructs the caller to
  `register_agent` for a fresh token; on 11.6.2 `register_agent` returned the
  dead token, so the prescribed recovery could never have succeeded.

- **Isolation is clean:** a freshly registered name mints a working token
  instantly and sends real messages. The mint path is healthy; the `chief`
  record specifically is not.

- **Cleanup debt:** `chief-dmcheck-1536`, registered to verify the DM path
  end-to-end, could not be deleted because `agent remove` is broken. It is
  still in the workspace.

- **Replay-of-completed-sessions ask** arrived from Khaliq via `factory-lead`.
  Routed onto `workstreams/intent-trajectory-lineage.md` rather than opened as
