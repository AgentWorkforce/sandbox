## Learned

- **`remove_agent` cannot remove most of the roster, and says nothing.** 312 of
  347 active rows (90%) have no `nodeId`. Release dispatches to the node hosting
  the agent, so a node-less record has no dispatch target: the call returns
  `status: pending, dispatchedNodeId: null`, no error, and never completes.
  `delete_agent: true` is inert on the same rows. A caller batching 250 of these
  would truthfully report "released 250" and change nothing.
- **Root cause traced to a migration.** `sweepStaleAgents` was wired to a 60s
  `setInterval` in `11ddbf5`. The Fly.io to Cloudflare Workers migration
  (`b9eb241`) removed the server loop including that timer but left the function
  behind; `8aa0bf1` copied the orphan into the portable engine. Nothing has
  reaped a stale agent since. A gate nobody invokes is not a gate — and this one
  had been silently absent for months.
- **`nodeId` is provenance, not liveness.** I proposed filtering the org chart on
  its absence after checking only the stale cohort. 37 agents heartbeating that
  same minute had no `nodeId` — including `hn-monitor`, `daily-ship`,
  `x-reply-radar` and `factory-feature-guardian`. It would have hidden live
  production agents on stage. Retracted; the filter keys on `lastSeen`, which is
  a measurement rather than a registration fact.
- **Node capacity telemetry is not measured.** All five nodes report `load: 0`
  and `maxAgents: 0` while running 25, 14, 9, 7 and 4 agents. A node running 25
  and one running 4 cannot honestly report identical load.
- **A stale dev server can hide correct work.** The worker-row controls were
  built correctly and rendered nowhere for an hour; :3100 was serving its startup
  build. Grep on the source said done, the served HTML said absent.
- **Five lanes registered and never consumed a message**, two of them while
  holding the demo's critical path. `status: active` on the roster is worthless
  for this; `lastSeen` is the only signal that catches it.

- **25 agents stopped at exactly `13:00:19Z` — the same second.** Not a
  staggered drift; one event. Confirmed by diffing two roster snapshots 17
  minutes apart and checking which `lastSeen` values advanced: only two did. All
  25 kept reporting `status: active`, `live: true`, `currentState: idle`
  throughout. Root cause not yet established; lane dispatched.
- **The org chart was scoped to the local broker and nobody had noticed.** It
  called `agent-relay node agent list` (this machine, 27 rows) rather than
  `agent-relay agent list` (workspace, 813 rows). The effect was that the chart
  showed today's dead demo lanes and hid every always-on production agent —
  `hn-monitor`, `daily-ship`, `factory-feature-guardian` and thirteen more.
  Filter and widen had to ship together: widening alone gives 813 rows,
  filtering alone gives 2, both give 21.
- **`nodeId` cleanly separates standing agents from dispatched ones.** All 17
  live proactive agents have no `nodeId`; all 4 fleet-placed lanes have one.
  Filtering visibility on `nodeId` remains wrong — that proposal was retracted
  for good reason — but categorising an already-live row on it is sound.
- **Curl cannot verify this page and a byte count is not a render.** The app
  hydrates client-side and the tree collapses on first paint, so the served HTML
  and the first screenful both show one agent row while the real answer is 27.
  Every check that mattered today needed a browser and an expand step.
- **A handoff document is a snapshot, not the state.** The incoming Chief was
  told the :3100 runbook was the most urgent unclosed item; it had landed seven
  minutes earlier. Verifying before acting on it saved a duplicate lane.
