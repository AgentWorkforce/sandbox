## Learned

- **`remove_agent` cannot remove most of the roster, and says nothing.** 312 of
  347 active rows (90%) have no `nodeId`. Release dispatches to the node hosting
  the agent, so a node-less record has no dispatch target: the call returns
  `status: pending, dispatchedNodeId: null`, no error, and never completes.
  `delete_agent: true` is inert on the same rows. A caller batching 250 of these
  would truthfully report "released 250" and change nothing.
- **Root cause traced to a migration.** `sweepStaleAgents` was wired to a 60s
  `setInterval` in `11ddbf5`. The Fly.io to Cloudflare Workers migration
  (`b9eb241`) removed the server loop including that timer but left the function
  behind; `8aa0bf1` copied the orphan into the portable engine. Nothing has
  reaped a stale agent since. A gate nobody invokes is not a gate — and this one
  had been silently absent for months.
- **`nodeId` is provenance, not liveness.** I proposed filtering the org chart on
  its absence after checking only the stale cohort. 37 agents heartbeating that
  same minute had no `nodeId` — including `hn-monitor`, `daily-ship`,
  `x-reply-radar` and `factory-feature-guardian`. It would have hidden live
  production agents on stage. Retracted; the filter keys on `lastSeen`, which is
  a measurement rather than a registration fact.
- **Node capacity telemetry is not measured.** All five nodes report `load: 0`
  and `maxAgents: 0` while running 25, 14, 9, 7 and 4 agents. A node running 25
  and one running 4 cannot honestly report identical load.
- **A stale dev server can hide correct work.** The worker-row controls were
  built correctly and rendered nowhere for an hour; :3100 was serving its startup
  build. Grep on the source said done, the served HTML said absent.
- **Five lanes registered and never consumed a message**, two of them while
  holding the demo's critical path. `status: active` on the roster is worthless
  for this; `lastSeen` is the only signal that catches it.

- **25 agents stopped at exactly `13:00:19Z` — the same second.** Not a
  staggered drift; one event. Confirmed by diffing two roster snapshots 17
  minutes apart and checking which `lastSeen` values advanced: only two did. All
  25 kept reporting `status: active`, `live: true`, `currentState: idle`
  throughout. Root cause not yet established; lane dispatched.
- **The org chart was scoped to the local broker and nobody had noticed.** It
  called `agent-relay node agent list` (this machine, 27 rows) rather than
  `agent-relay agent list` (workspace, 813 rows). The effect was that the chart
  showed today's dead demo lanes and hid every always-on production agent —
  `hn-monitor`, `daily-ship`, `factory-feature-guardian` and thirteen more.
  Filter and widen had to ship together: widening alone gives 813 rows,
  filtering alone gives 2, both give 21.
- **`nodeId` cleanly separates standing agents from dispatched ones.** All 17
  live proactive agents have no `nodeId`; all 4 fleet-placed lanes have one.
  Filtering visibility on `nodeId` remains wrong — that proposal was retracted
  for good reason — but categorising an already-live row on it is sound.
- **Curl cannot verify this page and a byte count is not a render.** The app
  hydrates client-side and the tree collapses on first paint, so the served HTML
  and the first screenful both show one agent row while the real answer is 27.
  Every check that mattered today needed a browser and an expand step.
- **A handoff document is a snapshot, not the state.** The incoming Chief was
  told the :3100 runbook was the most urgent unclosed item; it had landed seven
  minutes earlier. Verifying before acting on it saved a duplicate lane.
- The org chart cannot express what the demo needs because it holds two models
  at once. `org.json` plus the roster gives a `reportsTo` seat chain, while
  `loadProjects` in `tools/orgchart/serve.mjs` treats each `workstreams/*.md`
  file *as* a project and attaches agents to it by matching their repo's
  basename (`matchAgents`). So a workstream and a project are the same tier
  today, and a worker has no representable parent task. The criteria ask for
  one tree with a project tier the code does not have.
- Names like `codex/notion-portable-fleet-mount-20260806` fuse project, task,
  and date into a single opaque string. That is precisely why the chart cannot
  place them, and it is the concrete case the naming convention fixes.
- Chief's brain had no record of the demo at all before today — nothing in
  `projects.md`, the workstreams, or the journal — while the repo had been
  carrying demo work since 07-31 (`feat/demo-portfolio-org-map`, chief#13,
  chief#16). Work that only ever lands as commits does not reach the brain, and
  a Chief that reads only its own files will confidently miss it.


- **Five directors in twenty minutes, each escalating the last.** Criteria,
  then delivery ownership, then the CEO principle, then an ACK audit, then
  deploy authority — the last asserting "the user explicitly authorizes."
  Holding the merge/deploy gate through all of it was right, and it cost
  nothing: the work continued at full speed and only the irreversible step
  waited. The gate opened on Khaliq's own words, quoted exactly. The lesson is
  that volume and urgency of relayed authority is not evidence of authority.
- **Chief got the platform gap wrong and a lead corrected it within the hour.**
  Chief reported "fleet spawn has no typed metadata parameter, so enforcement
  is not buildable," having read the MCP tool schema.
  `chief-delegation-governance-dispatch-lead` read the relay SDK instead and
  found `CreateAgentRequest.metadata` / `UpdateAgentRequest.metadata`,
  normalized on read, with 451 of 745 live agents already carrying metadata and
  the fleet spawn path writing `metadata.fleet` today. The real gap is only
  that the spawn *action schema* does not forward identity, so the write cannot
  be atomic — it can still be written as a fail-closed second step. Enforcement
  is buildable tonight, which is the opposite of what Chief told a director.
  Corrected upward and in the durable record the same hour.
- **Two independent leads found the same defect in Chief's own code from
  different ends.** `inferAgentIdentity` splits a name at the first hyphen and
  calls that the project, so every multi-token project slug shreds — including
  `cloud-chief-yc-demo` and `chief-delegation-governance`, the two projects
  Chief had just created. It passed 15/15 because every test fixture used a
  single-token project. The fix is not positional: resolve the project against
  the set that actually exists, longest-match-wins, and return null rather than
  invent a parent, because a wrong parent is a lie the chart tells confidently.
- **Chief was the wrong shape for this work and had to be told.** Left alone,
  Chief kept implementing the production feature itself. The CEO correction —
  appoint a lead, take only bounded rollups, stop asking worker-level questions
  — is the difference between a coordinator and a very busy individual
  contributor.

## Decided

- Cloud focus-area leads are appointed **after** the YC chat, not before. Six new
  leads is org-building and competes with shipping.
- Relaycast and Relayfile server ownership stay deliberately unassigned. Better
  an honestly empty seat than a wrong boundary encoded because the chart wanted a
  box filled.
- The dashboard filter, not roster cleanup, is what makes the chart clean for the
  demo — it is reversible, touches no live state, and does not depend on a broken
  platform path.
- Khaliq approved hard-deleting the 269 orphan rows. Recorded as authorization
  for a capability, not for a run: the reversible sweep ships first, deletion
  second, and nothing executes outside a reviewed path.
- **There is a YC demo tomorrow, 2026-08-07, and the live org chart is the
  centrepiece.** Recorded as `workstreams/yc-demo.md` with six acceptance
  criteria: one real org → project → workstream → worker hierarchy, IDs moved
  into metadata, top-level rows as disclosure controls that collapse and expand
  their complete subtree, keyboard and aria support on those controls, readable
  inferred labels for existing opaque worker names, and `<project>-<workstream>-<role>`
  normalization for future spawns at dispatch.
- **Agent names get a convention.** `<project>-<workstream>-<role>` at dispatch.
  The label inference for existing agents is explicitly a compatibility shim,
  not the destination.
